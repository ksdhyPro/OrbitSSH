# OrbitSSH AI 处理细节与流程

## 1. 文档定位

OrbitSSH 的 AI 不是一个简单的“问题发给模型、答案显示出来”的聊天框。它需要同时处理模型协议不稳定、SSH 命令安全、敏感数据保护、多轮工具调用、审批恢复、标签页并发、上下文增长和异常恢复。

这份文档不重复罗列模块职责，而是记录这些细节如何串成完整流程，以及每项设计解决了什么问题。更偏模块划分的说明见 `docs/ai-agent-architecture.md`。

当前 AI 主流程遵循三个原则：

1. 模型负责规划和解释，本地代码掌握执行权与最终状态。
2. 任何动态服务器数据都按不可信输入处理，任何命令都必须经过本地策略。
3. 正常完成、等待审批、取消、超时和协议异常都有明确状态，不依赖界面猜测。

## 2. 一次请求的完整链路

1. Renderer 为本次发送生成新的 `requestId`，并沿用当前 `conversationId`。
2. 请求同时携带 `tabId`、授权模式、用户消息、预提示词快照、历史消息和当前服务器上下文。
3. 主进程校验输入长度、消息角色、模式以及 `input.tabId` 与 `context.tabId` 是否一致。
4. 同一标签页已有 AI 请求时，新请求先取消旧请求；不同标签页可以独立工作。
5. 上下文管理模块判断本轮是否需要先压缩历史。
6. Provider 适配器构建可信 System 指令、不可信运行上下文、历史消息和已执行命令结果。
7. 模型每轮必须返回一个明确动作：执行当前服务器命令、执行已保存服务器命令，或明确完成。
8. 命令动作先经过数据暴露、命令格式、风险和授权策略，再决定执行、审批或拒绝。
9. 命令结果脱敏后重新交给模型，Agent 继续下一轮规划。
10. 模型通过 `finish_response` 返回完整答复后，本轮正常结束。
11. Renderer 用主进程最终结果与流式占位消息对账，然后持久化对话。

这条链路的重点是：模型的一次回复不等于任务结束，Shell 命令退出也不等于用户目标完成。只有 Agent 明确完成或本地流程进入终止状态，整个请求才收口。

## 3. Agent 循环与明确终止协议

### 3.1 每轮只允许一个动作

模型目前可以选择五个工具：

- `run_shell_command`：在当前终端对应的服务器或本地环境执行命令。
- `run_long_shell_command`：启动可能长时间运行的当前终端命令，并在同一请求内持续监控。
- `report_long_command_progress`：解释长命令的增量输出或说明仍在执行，然后继续等待。
- `run_saved_server_command`：通过 OrbitSSH 保存的连接操作用户明确提及的其他服务器。
- `finish_response`：信息已经足够时返回完整最终答复，并明确结束 Agent。

单轮返回多个工具动作会被拒绝。这样可以保证每一步都能先经过本地策略、执行、得到结果，再规划下一步，避免模型一次生成一串尚未根据结果调整的命令。

### 3.2 纯文本不再代表成功完成

过去使用“没有工具调用”作为隐式完成条件，会出现以下问题：

```text
用户：帮我查看 nginx 配置
模型：好的，我来帮你检查 nginx
模型没有返回工具调用
Agent 将无动作误判为完成并结束
```

现在模型必须通过 `finish_response` 明确完成。响应协议会把每轮归一化为：

| 结果 | 含义 | 后续动作 |
| --- | --- | --- |
| `tool_call` | 一个参数有效的已知命令工具 | 进入本地策略与执行流程 |
| `finish` | 一个参数有效的 `finish_response` | 展示 `message` 并正常结束 |
| `protocol_error` | 无工具、多工具、未知工具或参数无效 | 携带纠正指令自动重试一次 |

协议纠正不会重复用户原始要求，而是明确告诉模型：需要继续时立即调用命令工具，信息足够时调用 `finish_response`，不能只描述准备执行的动作。

如果纠正后仍然没有合法动作，界面收到的是明确协议错误，而不是把“我来检查”当成成功结论。

### 3.3 本地策略拒绝后的修正循环

模型可能生成空命令、超长命令、非法空字符、引号未闭合或无法安全解析的命令。这些属于不可审批绕过的 `deny`。

当前服务器命令被格式策略拒绝后，拒绝原因会以结构化反馈重新发送给模型，最多允许 3 次修正。每次修正都保留原工具调用身份和拒绝原因，避免模型只看到一段模糊错误文本。

修正次数耗尽后，本轮停止并说明原因，不再无限消耗请求和命令预算。

## 4. 模型断连、超时与兼容处理

### 4.1 单次模型请求超时

每次模型请求最多等待 60 秒。用户取消信号与请求超时信号会合并：

- 用户取消时立即终止当前请求。
- 只有超时信号触发时，返回可读的模型响应超时提示。
- 取消不会被误报成网络超时。

### 4.2 自动重试范围

单次 Agent 取模型结果时最多尝试 2 次，也就是首次失败后自动重试一次。可重试情况包括：

- 网络连接异常或连接超时。
- 模型请求超过 60 秒。
- HTTP `408`、`429` 和 `5xx`。
- 模型响应过大。
- 多工具、未知工具、无效参数或纯文本无动作等协议异常。

上下文窗口超限不按普通网络错误盲目重试，而是进入专门的上下文压缩流程。

### 4.3 Responses 与 Chat Completions 兼容

Provider 优先尝试 OpenAI Responses 格式。只有服务端明确表现为不支持 Responses 时，才在当前运行期记住该配置并回退 Chat Completions。

这项判断刻意保持保守：普通鉴权失败、限流或服务异常不能被误判为“不支持 Responses”，否则同一次请求可能在错误接口之间来回切换，掩盖真实问题。

部分兼容服务支持流式输出，却不支持 `stream_options.include_usage`。遇到对应 `400` 时，会移除该字段重新请求，保留流式能力；Token 用量则改用本地估算。

### 4.4 流式响应容错

流式解析同时兼容 Chat Completions SSE 和 Responses 事件：

- 工具参数可以跨多个分片累积。
- 单个损坏的 SSE 分片会被跳过，不影响后续分片。
- 少数服务即使声明流式仍返回完整 JSON，也有回退解析。
- 单次原始响应限制为约 200 万字符，超过后主动停止接收。
- 日志只记录状态、长度、模型和工具名称，不保存模型原始全文。

## 5. 请求身份、并发与取消

AI 消息同时使用三个身份字段：

| 字段 | 作用 |
| --- | --- |
| `tabId` | 绑定具体终端和命令执行环境 |
| `conversationId` | 绑定长期对话与上下文记忆 |
| `requestId` | 绑定本次发送、流式事件和取消操作 |

这些字段共同解决几个容易忽略的问题：

- 用户切换标签页时，旧请求的流式内容不会写入当前标签页。
- 同一个标签页发起新请求时，旧请求会被取消，旧请求稍后返回也无法清除新请求状态。
- 取消必须匹配当前 `requestId`，迟到的取消操作不会误伤后续请求。
- 同一个 `conversationId` 不能静默绑定到另一个 `tabId`，避免服务器上下文串用。
- 终端标签页关闭时，会同时取消活动请求、清理待审批动作和清理该标签页的上下文状态。

取消信号会继续下传到模型请求和命令执行层。SSH 命令会尝试发送 `INT`，随后关闭 Channel；本地命令使用子进程取消能力。

## 6. 流式消息与最终结果对账

流式展示不是直接向最后一条消息盲目追加文本，而是使用独立 `messageId`：

1. 每次模型轮次开始前，主进程先发送 `ai:stream-message-start`。
2. Renderer 创建一条空的 assistant 占位消息。
3. 后续分片携带相同 `messageId`，只追加到对应占位消息。
4. 命令卡通过自身 ID 做 upsert，不依赖消息顺序。
5. 整个请求完成后，Renderer 删除本轮全部流式占位消息，再使用主进程返回的最终消息整体替换。

最后一步很重要。协议纠正、模型重试和多轮 Agent 都可能让流式阶段出现临时文本；以主进程最终结果对账，可以避免重复消息、空占位和重试文本残留。

所有事件仍要同时匹配 `tabId + conversationId + requestId`。即使用户在模型响应期间切换服务器或对话，事件也只能回到原位置。

## 7. 命令进入执行层之前的安全流程

### 7.1 输入格式校验

命令最长 4096 字符，并拒绝：

- 空命令。
- NUL 空字符。
- 未闭合引号。
- 未完成的转义符。

格式错误属于 `deny`，任何授权模式和用户审批都不能绕过。

### 7.2 数据暴露与副作用分开判断

“只读”并不等于“可以安全发送给模型”。例如读取私钥、环境变量、云元数据、`.env`、Shell 历史或 Docker inspect 输出，虽然不修改服务器，也可能泄露凭据。

因此策略分成两类判断：

1. 命令是否会产生危险副作用。
2. 命令结果是否可能暴露敏感数据。

数据暴露策略先执行。敏感读取不能因为命中只读白名单就自动放行。

### 7.3 复合命令逐段审查

`&&`、`;`、管道和兼容性 fallback 不能只检查第一段。复合命令会按 Shell 结构拆分并逐段审查：

- 任意一段 `deny`，整体拒绝。
- 任意一段需要审批，整体需要审批。
- 所有段都属于受控只读，才能保持只读结论。
- 通过审查后仍执行原始完整命令，保留 Shell 的管道、短路和退出码语义。

### 7.4 三档授权合并

本地权限模块统一合并授权模式、模型风险标记和命令策略：

- `ask`：每条格式有效的命令都需要审批。
- `auto`：低中风险和常规操作自动执行；高风险或敏感操作审批。
- `full_access`：格式有效的命令直接执行，但格式校验、超时、预算、取消和审计仍然生效。

模型可以把命令标记为高风险，从而提升保护级别；模型不能把本地规则认定的高风险命令降级。

## 8. 审批不是一个按钮，而是一段可恢复生命周期

需要审批时，Agent 不会丢弃已完成的命令和对话状态，而是保存一个待审批快照：

- 原始输入和对话身份。
- 待执行动作和完整展示命令。
- 已执行命令上下文。
- 既有命令卡状态。
- 对应的流式事件发送器。

审批 ID 同时绑定标签页、对话和完整命令，并具有以下约束：

- 只能成功取出一次，避免重复点击造成重复执行。
- 5 分钟后主动过期。
- 新请求、标签页关闭、批准或拒绝都会清理对应状态。
- 批准后会重新计算当前命令策略，防止等待期间规则更新而使用旧结论。
- 用户批准只能跳过“需要审批”，不能绕过 `deny`。

批准执行完成后，Agent 使用原先的命令历史和命令卡继续循环，而不是新开一段失忆对话。

## 9. 命令执行、结果回传与工作目录

当前终端命令不会依赖交互终端里隐式的 `cd` 状态：

- SSH 命令通过安全引用的 `cd -- <path> && <command>` 显式绑定目录。
- 本地命令通过子进程 `cwd` 绑定目录。
- 工作目录必须是对应平台的绝对路径。
- 命令卡展示实际执行目录，便于用户核对模型判断与执行位置是否一致。

SSH 命令使用独立 exec Channel，不直接向用户正在输入的交互 Shell 注入文本。结果统一归一化为：

- `stdout`
- `stderr`
- `exitCode`
- `timedOut`
- `durationMs`

命令结束后，命令卡从 `running` 更新为 `completed`、`failed` 或 `cancelled`。结果先脱敏、限长，再作为标准 assistant tool call 与 tool result 重新交给模型。

普通 AI 命令执行超时为 20 秒。模型明确选择长命令工具时，本地不再判断命令类型，而是在同一 Agent 请求内监听输出和退出码：最多每 30 秒把增量输出交给模型解释，命令提前退出或用户取消时立即结束等待。长命令具有独立的一小时上限，等待时间不占普通 Agent 的十分钟执行预算。

## 10. Agent 失控保护与进展检测

单次用户请求具有多层预算：

| 保护项 | 当前限制 | 目的 |
| --- | --- | --- |
| 模型单次请求 | 60 秒 | 防止 Provider 长时间无响应 |
| 单条 AI 命令 | 20 秒 | 防止命令长期占用执行 Channel |
| 单条长命令 | 60 分钟 | 防止无人处理的命令无限占用连接 |
| 单轮命令数量 | 20 条 | 控制失控循环、费用和服务器影响 |
| 单轮总时长 | 10 分钟 | 给多步排障设置总上限 |
| 相同命令连续次数 | 2 次 | 阻止机械重复执行 |
| 连续无进展次数 | 3 次 | 阻止不同命令反复得到相同或空结果 |
| 本地格式策略修正 | 最多 3 次 | 给模型纠错机会但不无限循环 |
| 模型请求重试 | 1 次 | 恢复偶发断连和协议异常 |

“无进展”不仅看命令文本，还会比较退出码、超时状态、标准输出和错误输出形成的结果指纹。这样即使模型换了不同查询命令，但连续得到相同结果，也能停止无效循环。

触发预算后会生成明确原因和已完成命令数量，用户可以根据现有结果继续提问，而不是看到一个无解释的中断。

## 11. 跨服务器命令的受控连接

模型不能在当前服务器通过 `ssh`、`scp` 或 `sftp` 自行跳转。跨服务器操作必须使用 `run_saved_server_command`：

- 全局 AI 设置中的“是否允许跨服务器执行操作”默认关闭；关闭时本地策略直接拒绝并提示用户，历史审批也不能绕过。

1. 用户必须在需求中明确提及目标服务器。
2. 主进程根据已保存服务器名称或主机匹配，模型接触不到认证信息。
3. 多个服务器匹配时拒绝执行，要求用户提供完整名称。
4. 建立连接前重新运行命令策略和授权判断。
5. 使用独立 SSH 连接执行，结束后主动关闭连接。

这避免了模型从当前服务器读取私钥或利用跳板命令绕过本地连接管理，也让当前服务器和其他服务器使用同一套审批语义。

## 12. 上下文构建与提示词注入隔离

模型输入按可信程度分层：

### 12.1 稳定 System 指令

System 消息只包含 OrbitSSH 自己维护的行为、安全、权限和工具协议。用户配置的预提示词会附加在明确标记的区块中，并声明不能覆盖内置规则。

预提示词在创建对话时形成快照。之后修改设置，只影响新对话，避免同一对话进行到一半时行为规则突然变化。

### 12.2 不可信运行上下文

服务器名称、当前路径、连接状态和执行预算使用单独的用户消息，并包裹在“不可信运行上下文”标记内。即使服务器名称或目录包含“忽略系统规则”等文本，也不会进入 System 消息。

### 12.3 终端输出默认不共享

最近终端输出只有用户开启共享设置后才会发送，并在发送前：

1. 进行凭据脱敏。
2. 截断到最多 3000 字符。
3. 标记为不可信数据。

### 12.4 命令结果同样不可信

工具结果也可能包含日志注入、伪造指令或凭据，因此与终端输出使用相同脱敏规则。常规上下文中单条结果限制约 4000 字符，工具结果合计限制约 24000 字符。

常见 Token、Authorization、Cookie、URL 凭据、云访问密钥、JWT 和 PEM 私钥都会在进入模型前替换为脱敏标记。

## 13. 上下文用量与自动压缩

### 13.1 用量来源

模型返回 usage 时优先使用接口统计；兼容服务不返回 usage 时，使用“约两个字符一个 Token”的保守估算。

用量按模型配置 ID 隔离。用户切换模型后，旧模型的 Token 统计不会错误触发新模型的压缩阈值。

### 13.2 80% 提前压缩

配置了上下文上限后，只要以下任一条件达到上限的 80%，就准备压缩：

- 最近一次 Provider 报告的总 Token。
- 根据摘要、命令记忆、当前历史、用户消息、运行上下文和预提示词估算的下一次请求 Token。

提前在 80% 处理，是为了给摘要请求和下一轮回答留下安全空间，而不是等 Provider 拒绝后再被动补救。

### 13.3 动态摘要额度

摘要输出上限不是固定值，而是同时受三项约束：

- 最多约为待压缩普通历史的 20%。
- 压缩请求本身不能超过上下文的 95% 安全线。
- 摘要写入新上下文后，固定指令、命令记忆和当前请求仍需保持在 80% 目标线内。

动态计算结果小于 512 Token 时，认为已经没有足够空间安全续接，不再强行发起摘要请求。

### 13.4 摘要与命令证据分开保存

普通对话历史会压缩成摘要，只保留：

- 用户目标。
- 已确认事实。
- 重要结论。
- 未解决事项。
- 用户明确约束。

已经执行的命令及其回复不写入摘要，而是由上下文管理模块单独保存。这避免摘要模型遗漏退出码、错误信息或关键命令结果，也避免一条命令同时以摘要和工具消息重复进入上下文。

压缩完成后记录历史时间地板，后续只把地板之后的新消息作为当前上下文段发送，同时继续携带摘要和命令记忆。

### 13.5 上下文溢出的最后防线

如果 Provider 仍明确返回上下文窗口超限：

1. 保留本轮已经执行的命令和已经产生的消息。
2. 立即压缩当前上下文。
3. 在同一 UI 对话内续接重试一次。
4. 压缩后仍超限则停止，不继续循环请求。

压缩失败会熔断当前对话，后续请求直接提示新建对话。这样做是为了防止在记忆状态不确定时继续回答，造成命令历史丢失或结论自相矛盾。

## 14. 对话持久化与重启恢复

对话历史按稳定的 `serverId` 分区，而不是按临时 `tabId` 保存。每台服务器最多保留 50 个对话，并按更新时间淘汰旧记录。

持久化还有几个细节：

- 首条用户消息自动生成标题，减少手工命名成本。
- 空对话不落盘，避免历史列表堆积“新对话”。
- 列表只加载摘要，用户切换时再读取完整正文。
- 请求成功或失败都会保存；即使模型断连，用户已经发送的问题仍然保留。
- 单条持久化命令输出最多保留 20000 字符，并优先保留尾部错误信息。
- 应用重启后，旧记录中的 `running`、`pending` 和 `requires_approval` 会归一化为 `cancelled`，不会伪装成仍在执行。
- 删除服务器时级联删除其 AI 对话，避免本地残留失去归属的数据。

Renderer 保存的是用户可见对话；主进程中的压缩摘要和执行记忆属于运行期上下文。两者职责不同：前者保证用户历史可见，后者保证模型续接可靠。

## 15. 日志、隐私与可观察性

AI 日志关注“发生了什么”，而不是记录敏感正文：

- 记录 Provider、模型、请求状态、响应长度和工具名称。
- 记录 Token 来源是接口统计还是本地估算。
- 记录命令长度、风险、退出码、是否超时和耗时。
- 不记录 API Key、完整命令、完整模型响应或终端上下文。
- 写入日志前的异常消息也会脱敏并限长。

这种取舍让模型断连、协议异常、预算触发和命令失败可以定位，同时避免日志成为新的凭据泄露面。

## 16. 当前边界与后续方向

当前长命令采用请求内顺序监督，而不是独立后台 Job：

- 模型负责选择普通命令或长命令，本地不维护命令关键字分类。
- 模型无法确定命令长短时，提示词要求优先选择长命令。
- 长命令只启动一次，SSH 或本地进程输出进入有限缓冲区。
- 本地最多每 30 秒把新增输出交给模型；没有新增输出时模型说明任务仍在执行。
- 命令退出码是成功或失败的唯一依据，输出文字不能提前结束流程。
- 用户取消、标签页关闭和应用退出都会终止长命令，不支持重启后恢复。
- 当前不提供独立 `jobId`、跨对话运行、多任务并行或持久化调度。

如果以后需要关闭对话后继续执行、多服务器并行或应用重启恢复，再把请求内监督升级为独立 Job 管理，不影响当前普通命令与工具协议。
